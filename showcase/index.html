Information Systems Analysis and Design · PTIT 2026

From requirements to running code. One chain you can follow and check.

ABC Online Shop sells books, electronics and clothes online. The case lists seven problems that come from three root causes: product, stock and order data are kept in separate places, many updates are made by hand, and data is maintained inconsistently. The system answers the root causes: one shared database, updates triggered by business events, and an order lifecycle that every role sees in the same state.

Objectives and scope

Implemented: login (UC02), browse and search (UC04), product page (UC05), cart (UC06), checkout with cart validation (UC07, UC21), card payment (UC08), order tracking (UC09), order processing (UC14), inventory (UC15). Specified only: registration, profile, reviews, promotions, reports, supply.

R2 use casesR3 implemented scopeSPEC

Users

Customers (guest, new, VIP with a discount), sales staff (order board), warehouse staff (inventory). External: payment provider (simulated, cards ending 0002 are declined) and shipping provider (carrier and tracking number).

R1 context diagramB1 business processR4 to R8 detailed use cases

What makes the solution worth defending

Product, Category, details

Product keeps the common data once; the category names the detail table (book, laptop, phone, apparel). A new category with a known attribute set needs no new table.

Three layers, one transaction per step

Controller, Service, DAO, Model. Each service operation is one use case step in one database transaction; the payment provider is called outside it.

Rules where the data is

Cart (BR01 to BR03), Order totals (BR04), the status transition table (BR09); CHECK and UNIQUE constraints repeat the rules in the database.

What changed

  • responsibilities became operations: Cart.validate(): List<CartIssue>, Order.place(…)

  • Payment kept its subclasses PayCredit and PayCash

  • the rule sits with the data it checks (the cart knows its lines and prices)
  • one transition table instead of status checks in every screen
  • Totals in one place: checkout, order and tests compute the same numbers

  • BR01 to BR04 and BR09 are unit tested without a database (OrderRulesTest)
  • the order board shows only allowed actions: it asks OrderStatus.next(actor)

Database design and generation

The data model was designed from the specification before any code: conceptual, logical, physical, then the database that Visual Paradigm generates from the physical model.

Category, Product and the detail tables

category is a tree with detail_kind (BOOK, LAPTOP, PHONE, APPAREL). product holds identity and common attributes (sku, name, brand, price, stock, status). Each detail table has product_id as PK and FK with ON DELETE CASCADE. Clothes and shoes share apparel_detail because their attribute sets are identical.

Rejected: one table per product type (price and stock six times, a search over six tables); one wide table with empty columns.

The one difference: foreign keys. The script that VP writes for SQLite has none: SQLite accepts a foreign key only inside CREATE TABLE, and the generator does not put it there. The 22 foreign keys come from the relationship lines of the same D4, through the DDL export of the plugin script (db/vp/vp_ddl.sql), which is db/schema.sql. The first generation also taught something: every text column came out as integer until the columns took their types from VP's own type list for SQLite (essay section 4.2.3).

AI

AI search (Chapter 3)

Customers who do not type the exact product name found nothing. The AI search understands related words, misspellings, price limits, a spoken query and a photo, and shows why each product was found. It is a component of the information system like any other: specified, modelled, designed, tested and measured.

Text

TF-IDF vector space model learned from the catalogue; a lexicon of related words; spelling correction by Damerau-Levenshtein distance; "under 10 million" becomes a hard price filter (AI03).

Voice and photo

Speech to text in the browser, editable before it is sent (FR-S4). A photo is compared with the product pictures by colour histogram, edge directions and silhouette (FR-S5); it is never stored (AI05).

Trust

Every result shows its reasons (AI02); no hit means the keyword search runs and the page says so (AI04); an out-of-stock product counts 20 % less (AI07).

Key decisions

Product + Category + detail tables; order created before payment; one transition table for the status; one transaction per service operation; provider call outside the transaction; stock reserved by a conditional UPDATE. Reasons: DESIGN.md and essay chapter 4.

Limitations

9 of 21 use cases implemented; SQLite and a simulated payment provider; the photo search was not tested on a different photo of the same model; the lexicon is a list in the code; no CSRF token or login throttling yet. Next steps: essay section 5.13.
