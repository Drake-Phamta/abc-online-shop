Information Systems Analysis and Design · PTIT 2026

From requirements to running code. One chain you can follow and check.

ABC Online Shop sells books, electronics and clothes online. The case lists seven problems that come from three root causes: product, stock and order data are kept in separate places, many updates are made by hand, and data is maintained inconsistently. The system answers the root causes: one shared database, updates triggered by business events, and an order lifecycle that every role sees in the same state.

Objectives and scope

Implemented: login (UC02), browse and search (UC04), product page (UC05), cart (UC06), checkout with cart validation (UC07, UC21), card payment (UC08), order tracking (UC09), order processing (UC14), inventory (UC15). Specified only: registration, profile, reviews, promotions, reports, supply.

Users

Customers (guest, new, VIP with a discount), sales staff (order board), warehouse staff (inventory). External: payment provider (simulated, cards ending 0002 are declined) and shipping provider (carrier and tracking number).

R1 context diagramR4 to R8 detailed use cases

What makes the solution worth defending

Product and its four kinds

Product keeps the common data once. Its kinds (book, laptop, phone, apparel) are subclasses, stored with Table per subclass; the category names the kind. A new category of a known kind needs no new table.

Three layers, one transaction per step

Controller, Service, DAO, Model. Each service operation is one use case step in one database transaction; the payment provider is called outside it.

Rules where the data is

Cart (BR01 to BR03), Order totals (BR04), the status transition table (BR09); CHECK and UNIQUE constraints repeat the rules in the database, added by hand to the generated tables and marked "-- rule".

Benefit

  • negative stock is impossible (test)
  • a price change never alters old orders (OrderItem.UnitPrice is a historical fact)

Database design and generation

The data model comes before the code, and the database is generated from it. The class diagram D1 goes through Synchronize to Entity Relationship Diagram and gives D2, which is generated, not drawn. Generate Database then writes the DDL, and the business rules are added to it by hand.

Product and its four kinds (Table per subclass)

Product is a class with four subclasses: BookDetail, LaptopDetail, PhoneDetail and ApparelDetail. The inheritance strategy is Table per subclass (Open Specification → ORM Class Detail → Subclasses...), so VP makes one table for Product and one for each kind. The key column ProductId of a kind is its primary key and a foreign key to Product, with ON DELETE CASCADE added by hand. Category.DetailKind (BOOK, LAPTOP, PHONE, APPAREL) names the kind. Customer (CustomerVIP, CustomerNew) and Payment (PayCash, PayCredit) are stored in the same way.

In the code, ProductDAOImpl.asSubclass picks the subclass from Category.DetailKind, and each subclass overrides specs(): the product page shows the attributes of its kind.

Rejected: VP's default, Table per class hierarchy (one table with many empty columns); one table per concrete kind (the Product columns copied four times, and a foreign key for each kind in CartItem and OrderItem).

The same table in schema.sql: the rules added by hand

CREATE TABLE Orders (
  OrderId INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
  AddressId integer(10) NOT NULL,
  CustomerId integer(10) NOT NULL,
  OrderDate date NOT NULL,
  Status varchar(255) NOT NULL CHECK (Status IN ('PENDING_PAYMENT', 'PLACED', 'PAID', 'PROCESSING', 'SHIPPED', 'DELIVERED', 'CANCELLED')),  -- rule
  PaymentMethod varchar(255) NOT NULL CHECK (PaymentMethod IN ('CARD', 'COD')),  -- rule
  Subtotal integer(10) NOT NULL CHECK (Subtotal > 0),  -- rule
  Discount integer(10) NOT NULL CHECK (Discount >= 0),  -- rule
  ShippingFee integer(10) NOT NULL CHECK (ShippingFee >= 0),  -- rule
  TotalAmount integer(10) NOT NULL CHECK (TotalAmount = Subtotal - Discount + ShippingFee),  -- rule
  FOREIGN KEY (CustomerId) REFERENCES Customer (CustomerId),
  FOREIGN KEY (AddressId) REFERENCES Address (AddressId)
);

The generated DDL holds no business rule. AI

AI search (Chapter 3)

Customers who do not type the exact product name found nothing. The AI search understands related words, misspellings, price limits, a spoken query and a photo, and shows why each product was found. It is a component of the information system like any other: specified, modelled, designed, tested and measured.

Text

TF-IDF vector space model learned from the catalogue; a lexicon of related words; spelling correction by Damerau-Levenshtein distance; "under 10 million" becomes a hard price filter (AI03).

Voice and photo

Speech to text in the browser, editable before it is sent (FR-S4). A photo is compared with the product pictures by colour histogram, edge directions and silhouette (FR-S5); it is never stored (AI05).

Trust

Every result shows its reasons (AI02); no hit means the keyword search runs and the page says so (AI04); an out-of-stock product counts 20 % less (AI07).

Key decisions

Product with four subclasses (Table per subclass); tables generated by Synchronize, rules added by hand; order created before payment; one transition table for the status; one transaction per service operation; provider call outside the transaction; stock reserved by a conditional UPDATE. Reasons: DESIGN.md and essay chapters 4 and 5.

Limitations

9 of 21 use cases implemented; SQLite and a simulated payment provider; the photo search was not tested on a different photo of the same model; the lexicon is a list in the code; no CSRF token or login throttling yet. Next steps: essay section 6.13.

  2. Initial Node in the Customer lane.
  3. Action: "Open checkout", "Validate the cart: price, status, stock (UC21)" in the right lane.
  4. Decision Node (small triangle → Merge Node where branches meet again). No text in the diamond.
  5. Activity Final Node for each ending.
  6. Control Flow: from node to node; on a flow leaving a decision, double-click → Guard, e.g. "blocking issue" (VP shows it as [blocking issue]).
Sequence diagram (G5 to G7, G9 design)
  1. Actor: Customer at the left.
  2. Lifeline: open the lifeline's specification → Base classifier → the design class (OrderController), VP shows ": OrderController"; then right-click → Stereotypes → the role of its layer (form: boundary; controller, service, DAO: control; model class: entity), VP draws the icon.
  3. Message: drag from the sender's dashed line to the receiver's; type the call "placeOrder(customerId, addressId, method, expectedTotal)". For a reply: draw a Message back, open its specification → Action Type → Return (VP then draws it dashed).
  4. Self Message for a call to itself (check card format and expiry).
  5. Alt. Combined Fragment: drag around the messages; right-click → Operator (alt, loop, opt, critical); right-click → Add Operand for "else"; double-click the operand → Guard.

Creating an object (Order, CartItem): a Message whose Action Type is Create; the created lifeline starts at that message. An error exit (card declined, out of stock): a Combined Fragment with the operator break. Activation bars run from the call a lifeline receives to its last message.

Class diagram (A10 analysis, D1 data model, G1 to G4b, G8 design)
  1. Package (layered diagrams G1): drop a frame per layer, name it service, dao, …
  2. Class: name it; right-click → Add → Attribute "-total : long" (Alt+Shift+A) or Operation "+place(…) : Order" (Alt+Shift+O); stereotype interface or enumeration from right-click → Stereotypes.
  3. Association (small triangle → Composition for Order ◆ OrderItem): drag from whole to part; double-click the ends for multiplicity (1, 1..*) and role (items).
  4. Generalization: drag from the subclass PayCredit to Payment (small triangle), the same for BookDetail to Product.
  5. Dependency: from user to used class or package; right-click → Stereotypes → use.

D1 (data model) is A10 drawn again with what a database needs: give every attribute a type and a multiplicity (1 = NOT NULL, 0..1 = NULL), every class that is not a subclass an id attribute, every end of every association a multiplicity and a role name, and every class the stereotype ORM Persistable (right-click → Stereotypes). Then open the specification of Product (and of Customer, Payment) → tab ORM Class Detail → Subclasses... → select the subclasses → Table per subclass → Apply.

Context diagram (R1)
  1. External Entity: Customer, Sales Staff, Payment Provider…
  2. Process: one process for the whole system, named after it.
  3. Data Flow: from source to target, name the data that crosses the boundary; one flow in each direction for every external entity.

A context diagram shows only the system and what is outside it, so the Data Store tool (3) is not used.

Data model (D2 is generated, not drawn), database and code generation
  1. Draw D1 as a class diagram (see Class diagram above): types, ids, multiplicities, role names, «ORM Persistable», Table per subclass.
  2. Synchronize: right-click the background of D1 → Synchronize to Entity Relationship Diagram → OK. In the dialog Select Primary Key choose the id attribute of each table instead of Auto Generate → OK. VP creates D2 with the tables, columns and foreign keys; you do not draw an entity or a relationship. Then rename the foreign key columns (CategoryCategoryId → CategoryId, the Category self-reference → ParentId), rename the table Order to Orders (ORDER is an SQL keyword) and arrange the layout.
  3. Generate the database: ribbon Tools → DB → Generate Database; in the dialog press Database Options, tick SQLite; tick Generate DDL, leave Export to database unticked; choose the output path → OK. VP writes the DDL (db/vp/vp_ddl.sql). Then run db/make_schema.py (adds the rules by hand) and db/compare_schema.py (checks the result).
  4. Generate the code: Tools → Code → Instant Generator, language Java, tab Model Elements, tick the folder 5 Design, keep the default options, choose the output folder, Generate.
